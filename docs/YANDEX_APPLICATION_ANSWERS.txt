ОПИСАНИЕ ПРИЛОЖЕНИЯ ДЛЯ РАБОТЫ С API ЯНДЕКС ДИРЕКТА
====================================================

1. НАЗВАНИЯ МЕТОДОВ, КОТОРЫЕ ИСПОЛЬЗУЕТ ПРОГРАММА
-------------------------------------------------

Программа использует API Яндекс Директа v5 (JSON) и Reports API.

Методы API v5:
• Campaigns.get — получение списка рекламных кампаний
• AdGroups.get — получение групп объявлений
• Keywords.get — получение ключевых фраз
• Bids.set — установка ставок для ключевых фраз

Reports API:
• POST /reports — запрос отчётов со статистикой
  - CAMPAIGN_PERFORMANCE_REPORT — статистика по кампаниям
  - CRITERIA_PERFORMANCE_REPORT — статистика по ключевым фразам


2. СХЕМА И ПОСЛЕДОВАТЕЛЬНОСТЬ ВЫЗОВА МЕТОДОВ
--------------------------------------------

Программа выполняет ежедневную выгрузку данных по следующей схеме:

ЭТАП 1: Получение структуры аккаунта
    │
    ├─► Campaigns.get
    │   Параметры: SelectionCriteria={}, FieldNames=[Id, Name, Status, State, Type, DailyBudget]
    │   Результат: список активных кампаний
    │
    ├─► AdGroups.get
    │   Параметры: SelectionCriteria={CampaignIds: [...]}, FieldNames=[Id, Name, CampaignId, Status]
    │   Результат: список групп объявлений
    │
    └─► Keywords.get
        Параметры: SelectionCriteria={AdGroupIds: [...]}, FieldNames=[Id, Keyword, AdGroupId, Bid, Status]
        Результат: список ключевых фраз

ЭТАП 2: Получение статистики (Reports API)
    │
    ├─► POST /reports (CAMPAIGN_PERFORMANCE_REPORT)
    │   Параметры: DateRangeType=LAST_7_DAYS, FieldNames=[CampaignId, Impressions, Clicks, Cost, Conversions]
    │   Результат: статистика по кампаниям за 7 дней
    │
    └─► POST /reports (CRITERIA_PERFORMANCE_REPORT)
        Параметры: DateRangeType=LAST_7_DAYS, FieldNames=[CriterionId, Impressions, Clicks, Cost, AvgCpc]
        Результат: статистика по ключевым фразам

ЭТАП 3: Применение рекомендаций (по запросу менеджера)
    │
    └─► Bids.set
        Параметры: Bids=[{KeywordId, Bid}, ...]
        Результат: обновлённые ставки


3. ЧАСТОТА ВЫЗОВА КАЖДОГО МЕТОДА
--------------------------------

Регулярные вызовы (автоматически, 1 раз в сутки в 03:00):

┌─────────────────────────────┬────────────────────┬───────────────────┐
│ Метод                       │ Частота            │ Запросов/сутки    │
├─────────────────────────────┼────────────────────┼───────────────────┤
│ Campaigns.get               │ 1 раз в сутки      │ 1                 │
│ AdGroups.get                │ 1 раз в сутки      │ 1-10 (по кампан.) │
│ Keywords.get                │ 1 раз в сутки      │ 1-10 (по группам) │
│ Reports (CAMPAIGN)          │ 1 раз в сутки      │ 1-3 (с retry)     │
│ Reports (CRITERIA)          │ 1 раз в сутки      │ 1-3 (с retry)     │
└─────────────────────────────┴────────────────────┴───────────────────┘

Вызовы по запросу (вручную, не чаще 1 раза в час):

┌─────────────────────────────┬────────────────────┬───────────────────┐
│ Метод                       │ Частота            │ Запросов          │
├─────────────────────────────┼────────────────────┼───────────────────┤
│ Bids.set                    │ По запросу         │ 1-5 (батчами)     │
└─────────────────────────────┴────────────────────┴───────────────────┘

ИТОГО: до 50 запросов в сутки (при 10 клиентах)
На начальном этапе (до 10 клиентов): 20-50 запросов в сутки


4. ОБРАБОТКА ОШИБОК
-------------------

Программа классифицирует ошибки по категориям и применяет соответствующую стратегию:

А) ОШИБКИ АВТОРИЗАЦИИ (коды 52, 53, 54)
   Стратегия: НЕ повторять запрос
   Действие: логирование, уведомление администратора, прекращение работы

   Пример обработки:
   - Код 52 (недействительный токен) → записать в лог, отправить уведомление
   - Код 53 (недостаточно прав) → записать в лог, пропустить операцию
   - Код 54 (пользователь заблокирован) → записать в лог, остановить обработку

Б) ОШИБКИ ЛИМИТОВ (коды 506, 9000)
   Стратегия: ожидание и повтор
   Действие: пауза 60 секунд, до 3 повторных попыток

   Пример обработки:
   - Код 506 (превышен лимит запросов) → ждать 60с, повторить
   - Код 9000 (превышен лимит операций) → ждать до сброса лимита

В) ВРЕМЕННЫЕ ОШИБКИ (коды 1000, 1001, 1002)
   Стратегия: экспоненциальная задержка (exponential backoff)
   Действие: повтор с увеличивающейся задержкой

   Схема повторов:
   - Попытка 1: сразу
   - Попытка 2: через 1 секунду
   - Попытка 3: через 2 секунды
   - Попытка 4: через 4 секунды
   Максимум: 3 повторные попытки

Г) HTTP ОШИБКИ (5xx)
   Стратегия: повтор с экспоненциальной задержкой
   Действие: до 3 попыток с увеличивающейся задержкой

   Пример:
   - HTTP 500 → ждать 1с, повторить
   - HTTP 502 → ждать 1с, повторить
   - HTTP 503 → ждать 1с, повторить

Д) ОШИБКИ ДАННЫХ (коды 8xxx)
   Стратегия: НЕ повторять
   Действие: логирование, пропуск операции, продолжение работы

   Пример:
   - Код 8000 (объект не найден) → записать в лог, пропустить
   - Код 8800 (недопустимое значение) → записать в лог, пропустить


5. УЧЁТ ОГРАНИЧЕНИЙ API ДИРЕКТА
-------------------------------

А) ОГРАНИЧЕНИЕ ЧАСТОТЫ ЗАПРОСОВ (5 запросов в секунду)

   Реализация: Token Bucket алгоритм

   Принцип работы:
   - Между запросами выдерживается интервал минимум 200 мс
   - Перед каждым запросом проверяется количество запросов за последнюю секунду
   - Если лимит достигнут, программа автоматически ждёт освобождения слота

   Код реализации:
   - Хранится список временных меток последних 5 запросов
   - Новый запрос выполняется только когда самая старая метка > 1 секунды назад
   - Минимальный интервал между запросами: 200 мс

Б) ОГРАНИЧЕНИЕ НА КОЛИЧЕСТВО ОБЪЕКТОВ В ЗАПРОСЕ

   - Максимум 10 000 ID в одном запросе
   - При необходимости обработать больше объектов — автоматическое разбиение на батчи

   Пример: если нужно обновить 25 000 ставок
   - Батч 1: Bids.set с 10 000 ставками
   - Батч 2: Bids.set с 10 000 ставками
   - Батч 3: Bids.set с 5 000 ставками

В) РАБОТА С REPORTS API

   Программа учитывает асинхронную природу Reports API:

   1. Отправка запроса на формирование отчёта
   2. Проверка статуса:
      - HTTP 200 → отчёт готов, получаем данные
      - HTTP 201 → отчёт формируется, ждём
      - HTTP 202 → отчёт в очереди, ждём
   3. Интервал проверки: по заголовку retryIn (обычно 10-60 секунд)
   4. Максимальное время ожидания: 10 минут

   Заголовки запроса:
   - processingMode: auto (система сама выбирает режим)
   - returnMoneyInMicros: false (деньги в рублях)
   - skipReportHeader: true (без заголовка отчёта)
   - skipReportSummary: true (без итоговой строки)

Г) МОНИТОРИНГ БАЛЛОВ (Units)

   Программа анализирует заголовок Units в ответах API:
   - Формат: "потрачено/лимит/остаток"
   - При достижении 80% лимита — предупреждение в логах
   - При достижении 95% — приостановка запросов до следующего дня


6. ДОПОЛНИТЕЛЬНАЯ ИНФОРМАЦИЯ
----------------------------

Язык программирования: Python 3.11+
Протокол: JSON (API v5)
Библиотеки: requests, pandas

Назначение приложения:
- Автоматизация регулярной работы по управлению кампаниями
- Синхронизация данных с внутренней CRM
- Анализ эффективности рекламы с помощью ML

Объём клиентов: до 10 аккаунтов на начальном этапе
Нагрузка на API: до 50 запросов в сутки (суммарно по всем клиентам)

Расписание работы:
- Ежедневная выгрузка: 03:00 (минимальная нагрузка на серверы Яндекса)
- Обновление ставок: по запросу менеджера в рабочее время
